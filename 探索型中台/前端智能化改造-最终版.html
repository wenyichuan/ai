核心思想

接入层变薄 · 决策层上移

这一节是整份 Demo 的思想主线：前端不是"不接后端"，而是把主要接入对象换成了 AI 执行层。下面的四条路径 Demo，全部是这条主线的落地证据。

趋势不是"前端不接后端"，而是 前端的接入层在变薄，智能决策层在上移
更准确地说：前端正在越过传统的"业务后端"，直接对接"AI 能力层"（模型 / MCP / Harness），而传统后端正在被挤压成纯粹的数据与事务执行层。

以前 · 一个意图 = 一个接口

用户点"智能排序" → 前端调后端 /api/sort → 后端执行 SQL 排序 → 返回数据。 不少新诉求需要新增或调整接口，前端通常要和后端一起排期才能落地。

现在 · 一个意图 = 一串工具调用

用户说"优先展示高优先级且快截止的任务" → 前端把意图发给 MCP Server → Agent 拆任务 → 调后端 /api/tasks 拿原始数据 → 调模型写排序函数 → 调前端 render 工具重新渲染。 整个过程前后端不直接对话，都听 MCP 这个"大脑"指挥。

03 · 边界为什么不能完全抛开后端？
!

数据安全与权限

数据库账号、用户身份令牌、付费业务逻辑，永远不能交给大模型处理，必须留在自建后端或 Harness 执行引擎里。前端声明的上下文（含 user 段）只是 hint：服务端必须基于会话重新鉴权，永不信任前端自报的身份。

⇄

事务一致性

"下单扣库存并发货"这种强一致性操作，必须由后端事务保证，大模型干不了这个细活。

¥

成本与延迟

每次操作都过模型成本受不了。MCP / Harness 会把高频、确定的操作（"翻到下一页"）直接路由给后端，只有模糊意图才过模型。

口径：月按 30 天；费用 = Token ÷ 1,000,000 × 单价。把「L1 直通率」拉到 0% 看看——那就是"所有操作都过模型"的账单，也是"前端直接调大模型"方案的真实成本。直通率每提高 10 个百分点，节省线性放大；右上角的「规则 / 模型」计数器，就是这个直通率的现场版。

¥降本四手段 & 降级阶梯（生产必备）

把成本再压下来的四个手段
意图缓存：同模板命中即复用解析结果（TTL + 参数槽位） 工具描述精简：只发当前场景相关的 5~8 个工具 流式优先：SSE 先回"我打算这么做"再执行 预算配额：按人 / 按会话设 Token 上限，超限降级 L1

第二条与「上下文锚定」是一体两面：scene 锁定能力域后，候选工具从 137 个缩到 5~8 个——省 Token 的同时把选错率打下来。另外，工具的 description 就是给模型看的接口文档，它的质量直接决定调用成功率。

降级阶梯：AI 不可用 ≠ 页面不可用
① 模型超时 / 不可用 → 自动回落 L1 规则，提示"当前为快捷模式"
② 连续 2 次解析失败 → 弹出结构化筛选面板，让用户手动补齐
③ 工具执行失败 → 展示失败原因 + 建议的替代意图，不干报错
④ 传统按钮全程保留——AI 是可选的加速器，不是必经的关卡

01
不要在 Vue 里直接调大模型 API（这是新手最容易犯的错）——会把 API Key 暴露在前端，且无法管控成本。
02
前端的新职责是"当好 MCP 的客户端"：在 Vue 里启动一个轻量级 MCP 客户端，把用户操作转成 MCP 的 tool call，然后把执行结果渲染到页面上。
03
后端的新职责是"把自己封装成 MCP 的 Tools"：把原来的 /api/createOrder 封装成 create_order Tool，注册到 MCP Server 上，让 AI 大脑去调用它，而不是让前端直接调。
05 · 上下文锚定前端给 MCP「带路」：声明场景与意图，而不是让它猜

网关有了「大脑」还不够：后端 MCP Server 里有几十上百个工具（tools/list），只靠工具描述去匹配，AI 经常选错或犹豫。前端明明知道用户在干嘛——在哪个页面、点了哪个按钮、想达成什么目的——却没告诉网关。解法是上下文锚定（Context Anchoring）：前端每次调用主动声明「我在哪、我要干嘛」，后端从「盲人摸象」变成「定向执行」。本页其实已经在做最小版：路径一的规则解析 = 意图解析器、工具注册表 = 能力域、角色选择 = 上下文里的 user。

// 前端每次调用 MCP 自动携带的「上下文信封」 interface MCPContext { scene: { id:'order_detail', name:'订单详情页', module:'order', route:'/orders/detail/123' } intent: { action:'update', target:'Order', trigger:'button_click', buttonId:'btn_approve' } payload: { orderId:'123', selectedIds:[], formData:{} } // 页面数据快照 user: { role:'operator', permissions:['order:read','order:update'] } } // 调用方式 1：声明式调用 __router__，后端按上下文定向执行 mcp.callTool('__router__', { userInput:'审批这个订单', _mcp_context:ctx }) // 调用方式 2（更彻底）：前端只说人话 mcp.execute({ goal:'审批这个订单', context }) // → 后端 AI 根据 goal + context 自动选工具执行

上下文由前端自动采集：路由 → scene、点击的按钮 → intent.buttonId、全局 store → payload、登录态 → user。开发者只声明语义，不拼参数、不背工具名。
哪些留在前端、哪些必须上移？采集、呈现、高危确认 UI、降级兜底留在前端；解析、权限裁决、配额计费、审计落库、Tool 执行必须上移网关与后端——前端校验只管体验，网关校验才管安全。

语义函数调用

前端只描述目标与约束：mcp.execute({ goal:'把最近 3 天未支付订单催一下', constraints:{ maxCalls:10, avoid:['VIP'] } })——后端 Agent 自动：查询 → 过滤 VIP → 限 10 个 → 发短信。AI 原生应用首选。

📡

事件驱动 MCP

前端不发请求，只广播事实：mcp.emit('order.approved', { orderId })——后端订阅事件自动完成：更新状态、通知仓库、记录审计、财务结算。前端完全不需要知道「调哪个工具」。

🧩

声明式 MCP

在路由配置里声明能力与按钮绑定：<Button mcp-action="approve_order">，页面加载自动 order.query、点击自动对应 action，上下文从路由 / state 自动提取。低代码平台首选。

方案前端工作量灵活性适合场景
上下文注入手动 setContext中中传统企业应用，改造成本最小
自动采集 + 智能路由推荐基座低高大部分业务系统
语义函数调用goal + constraints极低极高AI 原生应用
事件驱动 MCPemit / subscribe极低高异步流程 / 微服务
声明式配置mcp-action / 路由级声明极低中低代码 / 配置化平台

推荐组合：自动采集 + 智能路由做基座，声明式 mcp-action 做开发体验——前端只在按钮上声明语义，其余全自动。

L0

菜单 + 表单 + 按钮，逻辑写死，每个诉求都等排期——人适应系统。

L1

高频路径自动化：快捷指令、表单纠错，0 Token、确定性强（路径一勾选 L1 即此级）。

L2
单点智能

数据自己会说话：异常高亮、拐点标注、智能摘要（本页路径二）。

本页主体 · L3
L3
意图驱动

自然语言 → 网关编排 + 上下文锚定 + 五道闸护栏——系统适应人。

L4
自主编排

语义函数调用 / 事件驱动 / 声明式，MCP 感知消失。护栏没建好前不要跳到这级。

大多数团队站在 L0–L1。务实路线：L1 攒规则与信任 → L2 让数据说话 → L3 上网关与护栏 → L4 再谈消失；跳级 = 在没有白名单、Schema、审计时把编排权交给模型。注意区分两套编号：路径一里的 L1/L2 是路由层级（规则直通 vs 过模型），本表 L0–L4 是成熟度层级——重名纯属巧合，汇报时务必分开说。

落地

怎么落地 & 怎么算成功

四条路径不要同时上：先做信心工程，再打主战场；护栏与网关同期上线，不允许"先跑起来再加锁"。路径三看起来最酷、也最容易翻车——明确放最后并设边界。

P推进节奏 · 12 周四阶段（每步都有可验收产出）

P0 · 第 1–2 周 · 信心工程：先做路径二（智能数据层）+ 埋点基线——不改架构、零权限风险、一周见效，先拿组织信心。
P1 · 第 3–6 周 · 主战场：MCP 网关 + 路径一；3 个高频页面接入、20+ Tool 注册、五道护栏齐备。
P2 · 第 5–9 周 · 并行兜底：路径四（自愈 + 性能守护）+ 三级路由与预算配额。
P3 · 第 10–12 周 · 受控试点：路径三只开内部 1 个场景；先沉淀 15~20 个组件模板库，生成结果可保存为正式路由，再谈放开。

依赖关系不能颠倒：网关（P1）是路径一 / 三的共同前置；模板库依赖 P1 阶段提前约束的组件规范。风险预案：意图成功率不达标 → 工具集收缩到 5 个以内先做深；成本超预算 → 降 L3 占比 / 提高缓存 TTL / 换小模型；用户不买账 → 入口改成"操作建议卡"被动推荐。

8验收口径 · 八个数（上线前先埋点，别事后补）

意图成功率 ≥85% 平均操作步骤 ↓60% P95 意图首字节 <800ms L1 命中率 ≥60% 意图功能采用率 ≥30% Token ≤X 元/人/月（硬上限告警） 渲染类自愈率 ≥60% 越权 / Key 泄漏 = 0 起

每条意图记录四段式日志并上报后端：原始输入 → 解析计划（含是否过模型）→ 执行结果 → 用户是否撤销。正向飞轮：使用 → 日志 → badcase 归因 → 沉淀为 L1 规则 → 更快、更准、更便宜 → 更多人用。「用户撤销」是最值钱的负样本。

路径一

智能交互层 · 让界面"听懂人话"

一句自然语言 → 解析为受控的 tool call → 五道闸校验 → 执行 → 留痕。右侧每一步都对应落地方案里的护栏。这就是思想主线里「前端当好 MCP 客户端」的样子。换个角度看，五道闸就是幻觉的纵深防御：闸 2 拦「发明工具」、闸 3 拦「参数幻觉」、闸 4 拦「越权执行」、闸 5 拦「高危误操作」，审计兜底可回溯。一条铁律贯穿始终：模型提议 · 网关裁决 · 后端落地——提议权可以给 AI，执行权必须留在系统里。

1说出你的意图

L1 · 规则 + 意图缓存（"快捷指令"）
高频确定操作走正则 + 缓存复用。目标占比 ~70% · <50ms · 0 Token。本页开关勾选时即此级。
L2 · 小模型结构化解析
半确定意图（多条件组合、模糊时间）交给小模型，只输出 tool + params。目标 ~25% · 200~600ms · 成本低。本页"模型"模拟此级。
L3 · 大模型规划
真正的模糊意图（跨页编排、生成看板、多步任务）才请大模型做规划。目标 ~5% · 1~3s · 成本高（设上限）。

L1 开关这样对比着用：勾选时，"筛选北京已付款订单"这类高频说法命中规则库 → 30ms / 0 Token；关掉后同一句话改走 L2"模型"解析 → 结果相同，但慢约 600ms、花 150+ Token（看右上角 L1/L2/Token 计数，轨迹里也会提示"本可被 L1 命中"）。切换角色后再执行"删除订单"，可以看到权限闸生效。
