01 · 为什么现在要改

三个正在放大的痛点

痛点 1UI 意图被后端排期卡住

用户只是想"优先看高优先级、快截止的任务"，前端却要等后端加一个排序参数。一次交互诉求 = 一次跨端排期。

痛点 2功能越多，路径越深

筛选、排序、导出、对比、下钻……能力在增长，入口在堆叠。用户找不到、培训成本高，新功能使用率持续走低。

痛点 3数据会说话，界面不会

异常值、趋势拐点、环比突变都躺在表格里，靠人肉扫描。系统发现了问题，却没有机会告诉你。

判断

这三件事的共同点：都不是"数据问题"，而是 意图到执行之间缺少一层可编排的翻译器。这一层，就是 AI 执行层。

讲稿
开场不要先讲 AI，先讲痛：业务部门提一个排序需求走三周排期，这个例子最扎心。三个痛点都指向同一个根因——意图到执行之间缺一层翻译器。
02 · 核心判断

一句话讲清这次改造的方向

趋势不是"前端不接后端"
而是 前端的接入层在变薄，智能决策层在上移

前端正在越过传统的"业务后端"，直连 AI 能力层（模型 / MCP / Harness）；
传统后端正在被挤压成纯粹的 数据与事务执行层。

变薄前端接入层

不再为每个 UI 意图定制一个 HTTP 接口，而是把页面能力注册成一组可被调度的工具。

上移智能决策层

意图理解、任务拆解、工具编排、对话记忆，统一收敛到 MCP Server / Agent 网关。

下沉传统后端

退化为网关可调用的众多 Tools 之一：只做 CRUD、事务、权限，不再负责决策。

纠偏别理解成"前端直连大模型"

前端直连模型 = Key 泄漏 + 成本失控 + 无权限边界。正确姿势是 前端当 MCP 的客户端，后端把自己封装成 MCP 的 Tools。

04 · 职责边界

前端到底在接什么？——两样都接，但权重完全不同

接入对象接入方式权重（趋势）负责什么
AI 执行层
MCP / Harness		 MCP 协议
SSE / WebSocket		 核心 · 越来越重 意图理解、任务拆解、工具调度、对话记忆、权限校验前置
传统业务后端
CRUD / BFF		 HTTP / GraphQL
tRPC		 附属 · 越来越轻 纯数据增删改查、支付、发邮件等原子且强一致的操作

以前点"智能排序"

前端 → 后端排序接口 → 执行 SQL 排序 → 返回数据。
每个新诉求 = 一个新接口。

现在说"优先展示高优先级且快要截止的任务"

前端把意图发给 MCP Server → Agent 拆解 → 调后端取原始任务集 → 需要时调模型生成排序函数 → 回调前端 render → 全程前端与后端不直接对话。

一句话：前端依然要接后端，但中间夹了一层 AI 执行层。前端现在主要的对接对象，是这个执行层。

讲稿
这张表回答领导最常问的一句："那后端团队是不是没事干了？"——不是，后端从决策者变成被调度的执行者，事务和权限反而更纯粹、更重要。
05 · 边界与红线

为什么绝对不能完全抛开后端？

红线 1数据安全与权限

数据库账号、用户令牌、付费逻辑永远不能交给大模型。身份、租户隔离、字段级脱敏必须留在自建后端或 Harness 执行引擎内。

✕ Key 放前端✕ 模型直连 DB

红线 2事务一致性

"下单 + 扣库存 + 发货"这类强一致操作必须由后端事务保证。模型不保证幂等、不保证顺序，干不了这个细活。

✕ Agent 写多表✓ 单个事务型 Tool

红线 3成本与延迟

每次操作都过一遍大模型，成本和延迟都扛不住。执行层要把"翻下一页"这种高频确定操作直接路由给后端，只有模糊意图才过模型。

✓ 规则优先✓ 结果缓存✓ 模型分级

落地原则：三条不可让渡

① 权限不外包
模型只能提议调用哪个 Tool，能不能调由网关 + 后端说了算。

② 事务不外包
涉及写操作，一律封装成单一、幂等、可审计的事务型 Tool。

③ 成本不失控
默认走规则，模糊才过模型；按人 / 按会话设配额与预算上限。

边界：为什么不能抛开后端06 / 19
讲稿
这一页是"防守页"。一定会有人问"那直接上大模型不就完了"。三条红线对应三类真实事故：Key 泄漏、重复扣款、账单爆炸。

07 · 路径一 · 智能交互层

让界面"听懂人话"：意图 → 受控的 Tool Call

// composables/useAIExecutor.ts —— 关键：AI 只"点菜"，不"下厨"
type Tool = {
  schema: ZodSchema                       // 参数白名单
  risk: 'low' | 'high'
  run: (p: unknown) => Promise<unknown>
}
export function useAIExecutor(tools: Record<string, Tool>, ctx: string) {
  const loading = ref(false)
  const trace = ref<string[]>([])    // 执行轨迹：让用户看得见 AI 干了什么
  async function executeIntent(input: string) {
    loading.value = true
    try {
      // ① 确定性意图先走规则，命中就不花钱过模型
      const plan = matchRule(input)
        ?? await post('/api/ai/parse-intent', { input, ctx, tools: describe(tools) })

      // ② 工具必须在注册表内：杜绝模型"自己发明一个函数"
      const tool = tools[plan.name]
      if (!tool) throw new Error(`未注册的工具: ${plan.name}`)

      const params = tool.schema.parse(plan.params)        // ③ 参数契约
      if (tool.risk === 'high' && !(await confirmRisky(plan))) return   // ④ 高危确认

      await tool.run(params)
      trace.value.push(`${plan.name} ← ${input}`)
      audit.log('ai.intent', { input, plan })              // ⑤ 审计留痕
    } finally { loading.value = false }
  }
  return { executeIntent, loading, trace }
}
// 页面侧：把已有操作注册成工具
const { executeIntent, trace } = useAIExecutor({
  filterOrders: { risk: 'low',  schema: FilterSchema,
                  run: p => tableRef.value.filter(p) },
  sortOrders:   { risk: 'low',  schema: SortSchema,
                  run: p => tableRef.value.sort(p) },
  exportData:   { risk: 'high', schema: ExportSchema,
                  run: p => tableRef.value.export(p) },
}, '订单管理页：列表 / 筛选 / 导出')

效果一步到位

用户说"我要看最近一周北京地区的订单"，AI 自动组合筛选条件 + 时间范围 + 排序，跨多个控件一次完成。

保留传统按钮不删

自然语言是加速带不是替代品：高频操作保留按钮，长尾操作交给意图。

08 · 路径一 · 治理护栏

没有护栏的"AI 操作系统"，就是一个提权漏洞

闸 1工具白名单

模型只能从已注册的工具名里选，未知工具直接拒绝并记 badcase。绝不允许"生成一段代码然后执行"。

闸 2参数 Schema 校验

用 Zod / JSON Schema 校验参数，枚举值闭合。前端校验体验，网关校验安全，两侧都要做。

闸 3权限二次校验

模型说"调导出"≠ 有权导出。网关与后端各校验一次，前端的权限判断只用于隐藏入口。

闸 4高危二次确认

导出全量、批量删除、发起支付等 risk: 'high' 动作，必须把执行计划讲给人听并等待确认。

闸 5审计与回放

记录 原始输入 → 解析计划 → 执行结果 三段式日志，支持按人 / 按工具回放，badcase 可归因、可加规则。

禁止三类反模式

✕ 前端直连大模型（Key 泄漏）
✕ eval / new Function 执行模型输出
✕ 让模型直接拼 SQL 或写多表事务

一句话记住：模型负责提议，网关负责裁决，后端负责落地。提议权可以给 AI，执行权必须留在系统里。

09 · 路径二 · 智能数据层

让数据"自己会说话"：主动预警、解释、推荐

// composables/useSmartData.ts —— 修掉两个性能陷阱
export function useSmartData<T>(source: Ref<T[]>, rules: Rule<T>[]) {
  const insights = ref<Insight[]>([])
  const alerts   = ref<Alert[]>([])

  // ① 别对大数组深度侦听：每帧全量跑规则 = 主线程爆炸
  //    改为先算"数据指纹"（行数 / 极值 / 环比），指纹变了才跑
  const fp = computed(() => summaryOf(source.value))

  watchDebounced(fp, async (f) => {
    // ② 重规则丢进 Worker，主线程只负责渲染
    const r = await runRulesInWorker(rules, f)
    insights.value = r.insights
    alerts.value   = r.alerts
    r.alerts.filter(a => a.severity === 'high')
            .forEach(a => ElNotification.warning(a.message))
  }, { debounce: 300, maxWait: 1000 })

  return { insights, alerts }
}

原方案的两处隐患：① 对万行表格做深度侦听是灾难；② 规则同步跑在主线程，直接拖垮 FPS。已改为指纹 + 防抖 + Worker。

三个最快见效的场景

智能表格

异常值自动高亮并解释："这笔交易额是同类均值的 3.2 倍，建议关注"——把"发现"变成"提示"。

智能表单

输入即校验、补全、推荐："邮箱格式有误，是否修正为 xxx@xx.com？"——报错同时给解药。

智能图表

趋势变化时自动切换图表类型、标注关键拐点：减少"自己调图表"的操作。

为什么先做它：纯前端增量改造、不触碰现有架构与权限，一周可见效果，是最低风险的"信心工程"。

10 · 路径三 · 智能路由层

让页面"动态生成"：可以，但必须是受控生成

✕ 反模式：模板字符串动态 import
import(`@/components/${pageConfig.componentType}.vue`)

三个问题：

  • 路径不可控：模型返回的字符串可能指向任意组件 → 越权渲染
  • 产物 404：Vite 需 glob 预置，运行时拼接在构建产物里根本不存在
  • 无类型约束：拼错名字只能运行时才炸
✓ 正解：白名单注册表 + 类型约束
export const WIDGETS = {
  kpi:   () => import('@/widgets/KpiCard.vue'),
  table: () => import('@/widgets/DataTable.vue'),
  chart: () => import('@/widgets/EChart.vue'),
  map:   () => import('@/widgets/AMap.vue'),
} as const

// 模型只能输出 key，越界在编译期就报错
export function resolve(t: keyof typeof WIDGETS) {
  return defineAsyncComponent(WIDGETS[t])
}

// 网关返回的不是"代码"，而是受约束的页面 DSL
const pageConfig = {
  layout: 'dashboard-2col',
  widgets: [{ type: 'kpi',   bind: 'gmv' },
            { type: 'chart', bind: 'trend', chart: 'line' }]
}

收敛 1组件有限集

先沉淀 15~20 个业务组件构成模板库，模型只在库内组合。

收敛 2DSL 而非代码

网关输出声明式配置（布局 + 组件 + 数据绑定），前端只做渲染，永不执行生成的代码。

收敛 3可保存可分享

生成结果落库为正式路由并纳入权限体系，避免"每次都现生成"。

效果：用户说"给我一个销售数据看板"，页面自动生成 KPI 卡片 + 趋势图 + 明细表；但生成的是配置，不是代码——这是路径三能上线的前提。

11 · 路径四 · 智能运维层

让应用"自我修复"：只修已知模式，绝不猜业务

// plugins/self-healing.ts —— 修正原方案的两处致命写法
export const SelfHealingPlugin = {
  install(app: App) {
    // ✅ 原写法在同步回调里 await（SyntaxError）；
    //    errorHandler 本身可返回 Promise，声明 async 即可
    app.config.errorHandler = async (err, instance, info) => {
      const fix = await analyzeError(err, instance, info)
      if (fix.strategy === 'retry')   { retryRender(instance);   return }
      if (fix.strategy === 'degrade') { swapToFallback(instance); return }
      reportError(err, fix.suggestion)  // 未知错误：只上报，不猜
    }

    // 性能守护：采样 FPS，低于阈值才上报
    // 注意 performance.memory 仅 Chromium 可用，需可选链兜底
    useIntervalFn(() => {
      const fps = sampleFPS()
      if (fps < 30) suggestOptimization({ fps,
        heap: (performance as any).memory?.usedJSHeapSize })
    }, 5000)
  }
}

能力边界能自愈什么

  • 组件渲染异常 → 降级为备用组件 / 重试渲染
  • 资源加载失败 → CDN 切换、重试
  • FPS 低于阈值 → 关动效、开虚拟滚动、降级图表
  • 接口超时 → 切缓存 / 只读模式

绝不自愈什么

  • 数据 / 业务错误 → 只上报，不自动重试写操作（幂等风险）
  • 权限 / 鉴权失败 → 不重试，直接引导重新登录
  • 未知异常 → 不猜、不改业务代码，生成报告给开发者

定位：它是前三条路径的稳定性兜底，不是独立卖点。AI 引入的不确定性，需要它来对冲。

14 · 成本与性能

三级路由：把 80% 的请求拦在模型之前

L1规则 / 缓存优先

高频确定操作（翻页、排序、筛选、导出）走正则规则 + 意图缓存。

占比目标 ~70% · 延迟 < 50ms · 成本 0

L2小模型做结构化解析

半确定意图（多条件组合、模糊时间）走小模型做意图解析，只输出 tool + params。

占比目标 ~25% · 延迟 200~600ms · 成本 低

L3大模型规划

真正的模糊意图（跨页面编排、生成看板、多步任务）才请大模型做规划。

占比目标 ~5% · 延迟 1~3s · 成本 高（设上限）

四条降本手段

  • 意图缓存：同一意图模板命中即复用解析结果（TTL + 参数槽位）
  • 工具描述精简：只把当前页面相关的 5~8 个工具发给模型，别全量塞
  • 流式优先：SSE 先回"我打算这么做"再执行，感知延迟降低一半
  • 预算与配额：按人 / 按会话设 Token 上限，超限自动降级到 L1

降级策略（必须内置）

  • 模型超时 / 不可用 → 自动回落 L1 规则，提示"当前为快捷模式"
  • 连续 2 次解析失败 → 弹出结构化筛选面板，让用户手动补齐
  • 工具执行失败 → 展示失败原因 + 建议的替代意图，而不是干报错
  • 传统按钮全程保留，AI 永远不是唯一路径

核心原则：AI 是可选的加速器，不是必经的关卡。任何时候把它拔掉，系统都能正常用。

18 · 结论与 Ask

结论，以及需要今天的三个决定

结论：三句话

  1. 架构上：新增 AI 执行层（MCP / Harness），前端接入层变薄、智能决策层上移，后端退化为数据与事务执行层。
  2. 前端的新职责：当好 MCP 的客户端——把用户操作转成受控的 tool call，再把结果渲染出来。不要再在 Vue 里直接调大模型。
  3. 后端的新职责：把自己封装成 MCP 的 Tools，让网关调度，而不是让前端直调。

底线不变：权限不外包、事务不外包、成本不失控。模型只有提议权，执行权始终留在系统里。

最后一句：前端依然要接后端，但中间夹了一个 AI 执行层。前端现在主要对接这个执行层，由它决定是调后端、调模型，还是直接操作浏览器。

需要今天的三个决定

  • 立项范围：是否批准 P0 + P1（前 6 周：路径二 + 网关 + 路径一）作为一期范围？
  • 组织与归属：AI 执行网关由谁 owner？建议平台侧建网关、业务线注册 Tools，并明确各自 KPI。
  • 资源与预算：确认前端 2 人 + 后端 1 人 + 平台 1 人；模型预算按人均上限试运行一个月后复盘。
