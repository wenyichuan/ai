02 · 接入权重前端到底在接什么？两样都接，权重完全不同
接入对象接入方式权重（趋势）负责什么
AI 执行层MCP / Harness MCP 协议 / SSE / WebSocket 核心，越来越重 意图理解 · 任务拆解 · 工具调度 · 对话记忆
传统业务后端CRUD / BFF HTTP / GraphQL / tRPC 附属，越来越轻 纯数据增删改查 · 支付 · 发送邮件等原子操作

以前 · 一个意图 = 一个接口

用户点"智能排序" → 前端调后端 /api/sort → 后端执行 SQL 排序 → 返回数据。 每个新诉求 = 一个新接口，前端永远在等后端排期。

现在 · 一个意图 = 一串工具调用

用户说"优先展示高优先级且快截止的任务" → 前端把意图发给 MCP Server → Agent 拆任务 → 调后端 /api/tasks 拿原始数据 → 调模型写排序函数 → 调前端 render 工具重新渲染。 整个过程前后端不直接对话，都听 MCP 这个"大脑"指挥。

03 · 边界为什么不能完全抛开后端？
!

数据安全与权限

数据库账号、用户身份令牌、付费业务逻辑，永远不能交给大模型处理，必须留在自建后端或 Harness 执行引擎里。

⇄

事务一致性

"下单扣库存并发货"这种强一致性操作，必须由后端事务保证，大模型干不了这个细活。

¥

成本与延迟

每次操作都过模型成本受不了。MCP / Harness 会把高频、确定的操作（"翻到下一页"）直接路由给后端，只有模糊意图才过模型。

05 · 起步给你的三条实操建议
01
不要在 Vue 里直接调大模型 API（这是新手最容易犯的错）——会把 API Key 暴露在前端，且无法管控成本。
02
前端的新职责是"当好 MCP 的客户端"：在 Vue 里启动一个轻量级 MCP 客户端，把用户操作转成 MCP 的 tool call，然后把执行结果渲染到页面上。
03
后端的新职责是"把自己封装成 MCP 的 Tools"：把原来的 /api/createOrder 封装成 create_order Tool，注册到 MCP Server 上，让 AI 大脑去调用它，而不是让前端直接调。
// 一句话总结
前端依然要接后端，但中间夹了一个"AI 执行层"（MCP / Harness）。前端现在主要对接这个执行层，由它来决定是调用后端、模型、还是直接操作浏览器。
